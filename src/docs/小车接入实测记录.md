## ★ 头号陷阱：串口缓冲区里的陈旧数据（本次最大误判）

> 2026-10-11 查明。**这一个坑让我把软件问题误判成硬件故障，浪费了一整个排查阶段。**
> 任何后来者读串口前，必须先看这一节。

### 现象

| 表象 | 我当时的错误结论 |
|---|---|
| SDK `get_battery()` **10 次全 `None`** | "扩展板坏了" |
| `cat /dev/ttyAMA0` **0 字节** | "扩展板没通电" |
| 主动发 `0xAA55` **收到 0 字节** | "排线断了/接错口" |

**看起来像三条独立证据都指向"硬件故障"—— 其实全部是同一个软件原因的假象。**

### 真相

**扩展板从头到尾都在正常工作，一直在主动上报电池帧：**

```
aa55 00 03 04 9d1f 80 00      ← 反复出现，约 85 帧/秒
 │    │  │  │  │
 │    │  │  │  └─ 小端 0x1f9d = 8093 mV
 │    │  │  └──── func = 0x04（读电池）
 │    │  └─────── 长度 3
 │    └────────── func 0x00
 └─────────────── 帧头 0xAA55
```

**根因**：串口**接收缓冲区里积压了大量陈旧帧**。SDK 打开串口时没有先清空缓冲，
校验逻辑在垃圾数据里对不上帧头，于是**一律判 `None`**。

**决定性的对照实验**：

```
清空缓冲区之前 → get_battery() = None
清空缓冲区之后 → get_battery() = 8080 mV   ← 立刻就读到了
```

| 我发的 | 我收到的 | 真相 |
|---|---|---|
| 32 字节递增 `01 02 03...` | 128 字节 `aa55 00 03 04 9b1f...` | **是扩展板自己的上报帧**，不是回显 |
| 32 字节 `5a5a5a...` | 128 字节 `aa55 00 03 04 9b1f...` | 同上 —— 回读与我发的**完全不同** |
| 24 字节随机数 | 128 字节 `aa55 00 03 04 981f...` | 同上 |
| **什么都不发** | **3 秒收到 256 字节** | **扩展板在主动上报** |

> 关键判据：**回读内容与发送内容不同，且不发也在收 → 线路上有活跃设备，
> 不是回环、不是故障。**

### 为什么 `cat` 也是 0 字节

`cat /dev/ttyAMA0` 同样受积压数据影响 —— 但这个命令更难用，
因为它的读法、缓冲行为与 SDK 不同，**不能作为"串口是否正常"的判据**。

### 正确姿势（照抄）

```python
import serial, time

s = serial.Serial('/dev/ttyAMA0', 1000000, timeout=0.5)

# 【关键】先彻底冲掉积压数据，再读
s.reset_input_buffer(); time.sleep(0.5)
s.reset_input_buffer(); time.sleep(0.2)
print("剩余:", s.in_waiting)     # 应接近 0

# 然后逐帧同步：找 aa55 帧头
def read_frame(timeout=2.0):
    t0 = time.time()
    while time.time() - t0 < timeout:
        if s.read(1) != b'\xaa': continue
        if s.read(1) != b'\x55': continue
        hdr = s.read(2)                  # func + len
        func, length = hdr[0], hdr[1]
        body = s.read(length + 1)        # 数据 + 校验
        return func, body[:length], body[length]
    return None

# 或者：先清缓冲，再用 SDK
s.close()
import ros_robot_controller_sdk as rrc
b = rrc.Board(); b.enable_reception(); time.sleep(1.5)
print(b.get_battery())                   # → 8080
```

### 这次的教训（写给自己）

1. **"读不到数据" ≠ "设备坏了"** —— 先怀疑读取姿势，再怀疑硬件
2. **多个"独立证据"可能共享同一个错误前提** —— 三条路径都用同样的脏缓冲读法，
   所以三条一起错，看起来却像互相印证
3. **找一个能区分"故障"与"读取问题"的判决性实验** —— 这次是
   "清空缓冲前后对比"和"什么都不发看是否仍收到数据"
4. **不要急着下"硬件故障"的结论** —— 会导致建议用户拆机、返修，代价很大

- `tools/loopback_test.sh` —— **判决性实验**：区分回环 / 故障 / 主动上报
- `tools/read_battery_correct.sh` —— 正确读电池（含预清空）

## ⚠ 【最新】车不动的真因：串口无响应

> 2026-10-11 实测。**这推翻了之前所有关于“车不动”的原因猜测。**

### 完整链路追踪（逐段实测）

### 串口故障的多角度取证

**被排除的可能：**

| 角度 | 检查 | 结果 |
|---|---|---|
| GPIO 复用 | `pinctrl get 14,15` | ✅ `14:a4 TXD0`、`15:a4 RXD0` —— 正确 |
| 波特率 | `stty -F /dev/ttyAMA0` | ✅ `speed 1000000 baud`，`cs8 -parenb -cstopb` |

| 驱动 | `dmesg | grep ttyAMA` | ✅ PL011 UART 正常注册，无错误 |
| 端口权限 | `ls -l` | ✅ `crw-rw-rw-` |
| 时钟 | `/sys/class/tty/ttyAMA0/uartclk` | ✅ `50000000` |

**三条独立路径均证实“收不到数据”：**

```
1. SDK 读电池（开 enable_reception）  → 10 次采样全 None
2. raw cat /dev/ttyAMA0              → 0 字节
3. 主动发探测帧 0xAA55 / 电池请求    → 发出 2/6 字节，收到 0 字节
```

### 结论

**（当时的错误结论，见上文更正）**~~树莓派侧完全正常，主动发数据出去，但扩展板无回应。这是硬件层故障，不在软件配置。~~

**实际情况**：扩展板一直在主动上报（`aa55 00 03 04 9d1f`，约 85 帧/秒），

- 充电过程中**碰松了排线**，或
- **扩展板供电异常/固件挂死**，或
- 扩展板被接到了**错误的接口**（注意：机器上有 `/dev/ttyUSB0`，CH341 USB 转串口，与扩展板无关）

1. **扩展板指示灯**是否亮
2. **串口排线**（GPIO 14/15 到扩展板）是否松动、插对位置
3. **断电重启整机**（拔电等 10 秒再上），让扩展板重新初始化

## 【已解谜】电池读不到 —— 真相是串口无数据 + 类型冲突

**我之前两次归因都是错的**，如实记录：

| 我说过 | 实情 |

## 5. 【关键坑】启动脚本的日志重定向失效

`/tmp/start_turpi.sh` 与 README 的恢复命令都写成：

```bash
docker exec -d -u ubuntu -w /home/ubuntu turbopi /bin/zsh -c "
  source ~/ros2_ws/.zshrc >/dev/null 2>&1
  export PYTHONPATH=/opt/agh_mhs/python/src:\$PYTHONPATH
  cd /tmp && exec python3 -u /tmp/turpi_device.py $HUB > /tmp/turpi.log 2>&1
"
```

**问题有两个，都不是致命错误，但会误导排查：**

1. **重定向落在引号内层**。`> /tmp/turpi.log` 在 `-c` 的整段字符串里，被当作**进程内 shell 的重定向**，
   而不是外层 `docker exec` 的重定向——行为随引号解析而变，实测中该文件**始终停留在旧的
   597 字节 / mtime 13:33**，进程的输出进了黑洞。
   → 排查时**不能以 `/tmp/turpi.log` 是否存在新增来判断进程是否工作**。
2. **`pgrep -f turpi_device` 不可靠**。Linux `/proc/comm` 截断到 **15 字符**，
   `turpi_device.py` 为 14 字符但匹配模式含路径时会失效；实测曾因此误判"进程没起来"。
   → 用 `ps -o pid,ppid,cmd | grep turpi_device` 或 `pgrep -f turpi_device.py`。

**两种启动方式实测对比（本轮亲自对比）：**

| 方式 | 结果 |
|---|---|
| `docker exec -d ...` | ✅ **进程确实启动**（此前"失败"是 `pgrep` 误判） |
| 普通后台 `&`（经 ssh） | ✅ 同样启动；实测存活并拿到 **`PPID 0`** |
| 前台 `docker exec`（不加 `&`） | ❌ 阻塞 ssh，超时被杀 |

**结论**：README 里 `-d` 的用法**本身是正确的**，PPID=0 判据成立。
但**必须修掉重定向的引号层级**，否则日志永远看不到，故障排查会走弯路。

> 修法：把重定向放在 `-c` 字符串**之外**，或直接在脚本里 `exec 1>/tmp/turpi.log 2>&1`。

## 6. 【缺陷】电池字段恒为空 —— 上游无发布者（已定位）

现象：设备日志反复输出

```
turpi-01: state fields without a value yet: battery
```

**根因（已实测定位）**：设备**不通过串口 SDK 读电池**，而是订阅 ROS2 话题
`/ros_robot_controller/battery`（`std_msgs/Float64`，10 Hz，见 `turpi_device.py` L146）：

```python
Float64, "/ros_robot_controller/battery", self._on_battery, 10
```

实测该话题：

```
Type: std_msgs/msg/Float64
Publisher count: 0      <-- 没有任何发布者
Subscription count: 1   <-- 只有我们的设备在订阅
```

即 **`ros_robot_controller` 节点在跑（持有 /dev/ttyAMA0），但它没有发布电池话题**。

### 6.1 厂商节点存在名字遮蔽 bug

`ros_robot_controller_node.py`：

```python
# L38
self.battery_pub = self.create_publisher(UInt16, '~/battery', 1)

# L113  发布循环的门暴
while self.running:
    if self.enable_reception:          # 只有为真才发布
        ... pub_battery_data(...)

# L126  把方法名重新绑定成了 bool —— 遮蔽
self.enable_reception = msg.data
```

L27 只调了 `self.board.enable_reception()`（**板子**的方法），而发布循环看的是
**节点自己**的 `self.enable_reception`。两者不是一回事。

另外存在**类型冲突**：L38 声明 `UInt16`，而 `ros2 topic list -t` 把同一名字报为 `Float64`，
设备订阅的也是 `Float64`。

**影响（不只是"少个字段"）：**

- `battery_percent()` 永不返回有效值；

- 每个结果的 `after` 钩子本应附带 `battery_mv`，实际静默省略。

## 9. 【根因】双向进程互踢 —— 抖动的真因

这是本轮最重要的发现，**已修复**。

### 9.1 现象

- `turpi-01` 每 30–60 秒掉线一次，活动日志出现 `1006` 与 `Nerve channel closed`
- socket 端口不断变化（重连），send-Q 堆积 100–250 KB
- **日志停在 `audio: speaker unmute ok` 之后不再增长**
- 进程活着、socket 在、但数据不流

### 9.2 真因

实测发现**两个** `turpi_device.py` 进程同时在跑：

```
PID 20820  PPID 0     ← 本次启动的
PID 34826  PPID 2113  ← 更早的残留
```

两者**共用同一个 device id `turpi-01`**。`agnes_mhs/device.py` L443：

```python
log.error("%s: replaced by another connection with the same id; not reconnecting", self.id)
```

**同 id 的新连接会踢掉旧连接，且被踢者不再重连。** 于是两个进程反复抢占，
一个占着 socket 却什么都不做，另一个不断被踢 —— 这就是看到的所有怪现象。

### 9.3 佐证

清理到**只剩一个进程**后：

| 指标 | 双进程时 | 单进程后 |
|---|---|---|
| 日志 | 从不输出 `speaker unmute` | **首次完整走通启动流程** |
| 进程数 | 2 | **1**（`PPID 0`） |
| socket | 反复变化 | 建立两个通道（命令 + nerve），符合设计 |

### 9.4 清理方法（已验证）

见 `tools/clean_restart.sh`。要点：**容器内和宿主都要清**，且用 `ps` 而非 `pgrep`：

```bash
#!/bin/bash
# 容器内
for p in $(docker exec turbopi ps -eo pid,cmd | grep 'turpi_device.py' | grep -v grep | awk '{print $1}'); do
  docker exec -u root turbopi kill -9 "$p"
done
# 宿主（可能有在容器外启动的旧进程）
for p in $(ps -eo pid,cmd | grep 'turpi_device.py' | grep -v grep | awk '{print $1}'); do
  sudo kill -9 "$p"
done
# 必须验证为空再启动
ss -tn | grep ":4180" && echo '!! socket 残留' || echo '干净'
```

> ⚠ **启动前必须确认进程数为 0。** 每次重启前不检查，就会再次变成双进程互踢。

**错误写法**（重定向的是 `docker` 自己的 stdout，是空的）：

**错误做法**：只看 `netstat` 里有 ESTABLISHED 就认为通了。

4. 发 `drive` 前确认 `halt` 可用（同一通道，通道不健康时急停送不到）。

## 13. 【已解谜】`lost` 丢帧率 —— 不是故障，是设计行为

> 2026-10-10 晚实测确证。**推翻**了之前"hub 丢数据"与"统计假象"两种猜测。

### 12.1 现象

`turpi-01` 的 health 长期报 `Attention: front: 41% / 87% / 88% lost`，
且状态在 `available ↔ offline` 之间摇摆。

### 12.2 实测方法

用 north 接口（`/ws/hub`）连续读源，逐次记录 `seq`。
工具：`tools/probe_seq.mjs`（用法：`node tools/probe_seq.mjs 12 1500`）。

实测输出（节选）：

```
   0    front    577    2.93   front: 88 % lost
   2    front    584    0.79  <== 跳号 delta=7 (丢了 6)
   4    front    587    0.72  <== 跳号 delta=2 (丢了 1)
   6    front    590    0.66  <== 跳号 delta=2 (丢了 1)
   8    front    593    0.58  <== 跳号 delta=2 (丢了 1)
   9    front    594    1.04   ok              ← 持续读图后恢复 ok
  11    front    597       1   ok
```

**`pose` 同理**：`523 → 529 → 530 → 533 → 534 → ...`，同样 delta=2 跳号。

### 12.3 hub 的判定逻辑（`server/observe.ts` L56-58）

```typescript
if (stream.lastSeq !== undefined && msg.seq > stream.lastSeq + 1)
  stream.lost.push({ time, n: msg.seq - stream.lastSeq - 1 })
```

**只有当 `seq > lastSeq + 1` 时才计丢帧**。故 `lost` 确实来自 seq 跳号，
**不是**“内空时间被计入”的统计假象（我之前的猜测是错的）。

### 12.4 真因：MHS 的「最新优先」队列（STR-6 / STR-1）

`agnes_mhs/device.py` L168-179：

```python
def send(self, data, binary=None, ...):
    """Queues one message; returns False when it was not wanted. An unsent older message of this
    source is replaced, latest wins (STR-6), and its seq is skipped (STR-1)."""
    if not self.wants():          # L172  无需求就不发，不递增
        return False
    ...
    msg = {"type": "data", "source": self.id, "seq": self._seq, ...}
    self._seq += 1                # L179  seq 只在真正发送时递增
```

链条：

| 环节 | 实测 |
|---|---|
| 车取图速度 | **快**（快照接口 0.024–0.043 s） |
| `stream_camera` 推图频率 | 每 0.2 s 尝试一次 |
| **hub 消费速度** | **慢** ← 真正的瓶颈 |
| 结果 | 队列里旧帧被新帧替换，**被替换帧的 seq 永久跳过** |

即：**车发得比 hub 消费得快，队列按“最新优先”丢弃旧帧——这是规范定义的行为，不是故障。**

### 12.5 决定性佐证

持续读图后，`lost` 从 **88% 一路降到 `ok`**（见 12.2 的采样 9-11）。
因为有人消费了，队列不再积压。

> **结论：`lost` 高的时候正是“没人在看”的时候；一旦有人读，它就恢复 ok。**
> 实际取图完全正常（每次读 `age < 1 s`，图像 141908 字符 base64 完整）。

### 12.6 因此

- ❌ 不是链路故障（socket 稳定，端口不换）
- ❌ 不是 hub 丢数据（帧在 hub 缓存里，且新鲜）
- ❌ 不是双进程互踢（进程数 1）
- ✅ **是 MHS 设计行为**，`lost` 指标在空闲时必然偏高

> **实用建议**：不要拿 `lost` 百分比判断设备好坏。要看 **`age`**（秒级即正常）。
> 演示前不妨先读一次图，把队列“唤醒”。

### 12.7 仍未解释的

排查中发现两个**真问题**，与 `lost` 无关，不应用本次结论去掩盖：

1. **`turpi-01 rejected drive (offline): turpi-01 is not connected`** ——
   而车侧 socket 与进程均正常。hub 会话状态与车侧不一致。
2. **采样第 1 轮 `ERROR no data yet`** —— 两个源同时读不到。

两者都指向 **hub 侧会话状态抖动**，而非数据队列。待后续。
