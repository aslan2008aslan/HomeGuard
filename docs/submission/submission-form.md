### ▶ 粘贴内容开始

**一、项目概述**

HomeGuard 是一个面向家庭服务的机器人自主巡检框架。用户用一句自然语言下达任务，机器人自主完成"移动—观察—推理—验证—反馈"的完整闭环，并在判断不可靠时自动重试纠错。

本次参赛选择"绿植是否缺水"作为第一个验证场景：用一个真实、可运行、可复现的小场景，验证框架的完整闭环能力。换一条任务指令（如"看看厨房窗户关没关"），只需新增视觉判断规则与地点，核心代码不改。

**二、问题来源**

家庭服务机器人正从"遥控执行"走向"自然语言交互"，但真正的瓶颈不在单点能力，而在任务闭环。用户说一句"去看看阳台的绿萝要不要浇水"，机器人需要自己决定去哪里、看什么、怎么判断、判断不准怎么办、判断完之后怎么反馈。目前多数产品要么依赖预编程的固定流程，要么只能完成单步问答。

家庭场景是长尾的。若每个场景都单独开发一套流程，家庭机器人永远无法真正进入普通家庭。因此真正有价值的不是"会浇水的机器人"，而是一个能用自然语言即时定义任务、自主完成闭环、并在失败时自我纠错的通用任务引擎。

**三、实现方案**

**系统架构**

上位机（Windows）运行 Agnes Harness（AGH）+ AgnesHub + 模型；设备端为 Hiwonder TurboPi（树莓派 5），运行 MHS 设备程序。两端通过一条出站 WebSocket（设备 → 上位机 :4180）连接。

**关键设计决策：调用方向**

这是本项目最易被理解反、也最能体现协议层价值的一点：不是上位机去连小车，而是小车主动 dial 上位机的 AgnesHub。MHS 协议原文："A device dials AgnesHub, registers its state, tools and data sources, then takes calls and streams data. The model never talks to a device directly: it acts through AgnesHub, which checks every call against what the device declared."

这一设计带来三个好处：设备侧不开入站端口，只需一条出站连接，攻击面最小；协议层由 AGH 全包，不必写任何"调小车接口"的胶水代码；每次调用都按设备自己的申报校验，本身就是可直接展示的协议级安全证据。

**模型侧工具表**

模型侧固定只有 7 个设备工具（list_devices / read_device / call_device / set_device / stop_device / watch_device / unwatch_device）。设备自己的工具是 call_device 的参数，因此设备增减不改变模型的工具表，这是可扩展性的关键。其中 read_device 声明了 returnsImages，摄像头图片能直接进模型上下文——这是视觉推理能落地的技术前提。

**核心功能**

1. 自然语言任务理解：一句话描述巡检需求，自动解析为可执行步骤。
2. AGH 驱动的任务编排：模型完成"导航→观察→推理→验证→反馈"的步骤规划，AGH 负责工具调用、执行反馈与记录留存。
3. 视觉推理与不确定性处理：模型基于图像判断绿植状态，输出带置信度和依据的结构化判断（conclusion / confidence / evidence / retry_recommended）；置信度不足时自动换角度重拍并二次判断。湿度计读数与图像判断交叉验证。
4. 异常与边界处理：展示真实的失败自纠错与降级处理。
5. 任务切换能力：同一套系统不修改核心代码，输入新的自然语言任务即可验证框架通用性。

**设备能力申报**

turpi-01 申报工具：drive（前进/后退指定距离，带进度与暂停）、turn（原地转向）、change_view（换视角）、aim_camera（云台）、halt（急停）、say、listen；数据源：front（640×480 JPEG）、pose、mic。设备自带安全底线：限位、急停、与 hub 断连时自行停下。

**场景地图**

地图 home（6×4 米）含三个地标：dock（充电座）、plant（阳台绿萝）、window（厨房窗户）。

**四、AGH 执行流程**

任务输入："去看看阳台的绿萝要不要浇水"。六步闭环：

1. 解析意图、规划步骤——模型编排步骤序列。
2. list_devices / read_device 看电量与位置——状态感知，检查设备申报。
3. call_device(drive, plant) 开到绿萝前——按设备申报校验后转发。
4. read_device(front) 取图——returnsImages 把相机变成模型可读输入。
5. 置信度不足 → change_view 重拍 → 二次判断——执行反馈回灌，触发重试。
6. 输出结论 + 置信度 + 依据。

AGH 承担六个不可替代的环节：任务规划、能力调用（按设备申报校验）、图像进上下文、执行反馈回灌、安全约束（stop_device 总是允许）、记录留存。若不使用 AGH，上述六项全部需自行实现，且无法满足赛事的记录与核查要求。

**五、验证方法**

链路可用性验证先于一切。只看 netstat 里有 ESTABLISHED 就认为通了是错误的——实测多次出现"半死会话"：TCP 连接在，但 MHS 数据不流。因此建立六条判据：进程恰好 1 个且 PPID 0；日志在增长；socket 稳定不换端口；send-Q 不持续堆积；AGH 侧源时间戳秒级；相机能出图。

执行结果采用三层证据：调用层（每次 call_device 的入参、返回值、时间戳）、物理层（设备实际动作与状态变化）、判断层（模型的结构化判断与置信度）。

交叉验证：图像判断与湿度计读数对照；航位推算位置不单独作为精确值；电池字段与串口直读对照。

诚实标注：pose 源因无编码器会漂移，主动标注 ok: false；aim_camera 总是失败，故意保留以诚实报告失败。

**六、技术亮点**

1. 首个真实硬件接入案例。官方 MHS 验收范围明确不含物理设备（"Real browsers, paid models, external services, physical devices, and other platforms were outside this acceptance scope"）。本项目端到端跑通了真机接入。

2. 协议级安全。设备只申报自己具备的能力，AgnesHub 按申报校验每次调用；设备侧不开入站端口。

3. 诚实的系统设计。对不可靠数据如实标注（pose 标 ok: false），对失败的工具如实保留并报错。

4. 可扩展架构。模型侧工具表固定 7 个，能力是参数。

**七、异常与失败处理（真实案例）**

F1 · 双进程互踢（已定位并修复）。现象：设备每 30–60 秒掉线，日志出现 1006 与 Nerve channel closed，日志停在 "audio: speaker unmute ok" 后不再增长——进程活着、socket 在、但数据不流。根因：两个 turpi_device.py 进程共用同一 device id，agnes_mhs/device.py L443 明确"同 id 新连接会踢掉旧连接，且被踢者不再重连"。该症状与网络问题极难区分。修复：清理容器内与宿主全部残留进程，验证 socket 清空后只启一个。

F2 · 电池字段恒空导致低压保护失效（已定位，未修复）。设备订阅 ROS2 话题 /ros_robot_controller/battery，实测 Publisher count: 0。根因是厂商节点的名字遮蔽 bug：发布循环的门闩是 self.enable_reception，而 L126 把方法名重新绑定成了 bool，启动时只调了板子的 enable_reception()，节点自己的标志从未置位。影响不只是少个字段：设备侧低压安全闸 if mv is not None and mv < 6800 永远不会触发——电量再低车也不会拒绝运动指令。实际后果是小车曾因此跑到电量耗尽硬关机。这条说明：安全机制的失效往往不是显式报错，而是静默。

F3 · 云台恒失败（已知，设计如此）。舵机接受位置写入但带不动负载。系统故意保留该工具让它如实报错；降级方案是用 change_view 底盘转向代替。

F4 · 链路间歇抖动（部分改善，未完全定位）。双进程互踢修复后大幅改善，但 nerve 通道 send-Q 积压仍未定位。

此外，排查中推翻了多个假设并留档：HTTP 取图饱和（快照接口实测 0.07 秒）、线程池饥饿（200 并发压测线程数与 socket 完全不变）、Windows 防火墙拦截（真因是双进程互踢）。

**八、已实测验证的结果**

设备接入：list_devices 可见 turpi-01 且状态 available，7 工具 + 3 数据源，容器内进程 PPID 0。

前进 + 拍照闭环：read_device(pose) 确认在线 → call_device(drive, {distance: 0.5, speed: 0.1}) → read_device(front)。实测返回原文："turpi-01: drove 0.50 m forward. Now at (1, 0.5) facing 0 degrees, position not trusted. Took 5 s." 位置从 (0.5, 0.5) 到 (1, 0.5)，640×480 JPEG 成功进入模型上下文。

底盘运动：轮子实测转动（25% 占空比）；原地转向 angular.z=2.0 实测转动。电池读数：串口 SDK 直读 7306 mV，12 次采样稳定在 7303–7308 mV。音频链路：麦克风与喇叭共用同一 USB 声卡，实测回环播放 1kHz 时麦克风 RMS 从 0.016 升至 0.792。

**九、诚实声明的边界与限制**

1. 云台不可用：舵机接受位置写入但带不动负载，已用底盘转向代替。
2. 无编码器：位置靠时间积分会漂移，pose 源诚实标注 ok: false。
3. 转向换算缺陷：需 angular.z≈2.0 才能驱动轮子。
4. 低压保护失效：见 F2，演示前必须人工读取电压。
5. AgnesHub 无鉴权无加密：仅能在可信局域网内监听，禁止暴露公网。
6. 图像源约 41% 丢帧，取图偶有延迟。
7. 本次只把"绿植缺水检测"一个场景跑通，不堆场景、不拼功能数量。

**十、环境与依赖**

大模型：**DeepSeek V4.1 Flash**（上下文 **1M tokens**），经 Agnes Harness 调用，承担任务规划与视觉推理。上位机 Node.js ≥ 24.10，AGH 源码构建（官方暂无安装包）。设备端 Debian 12 aarch64，Python 3.11.2，容器内 ROS2 Humble。agnes_mhs 依赖 jsonschema、websockets。专业工具：ROS2 Humble、picamera2、PyAV、ros_robot_controller_sdk、MHS 协议层。本项目使用真实硬件，不使用仿真。

**十一、第三方素材来源与授权**

Agnes Harness 与 agnes_mhs 来自 github.com/AgnesAI-Labs/agnes-harness，授权 Apache-2.0。TurboPi 厂商 SDK、例程与 ROS2 工作区来自 Hiwonder（幻尔）随机预装，未再分发。本仓库仅包含团队原创代码，厂商组件不随本仓库分发。
**十二、后续迭代路线**

近期复用同一套机制，新增门窗巡检、煤气灶关闭确认、快递签收提醒，仅需新增视觉判断规则与工具接口。中期引入姿态估计与时序异常检测，扩展到老人跌倒检测、儿童独处异常提醒。长期愿景是家庭主动服务 Agent。
