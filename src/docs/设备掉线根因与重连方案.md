# 设备反复掉线：根因与重连方案

> 2026-10-11。本文回答一个问题：**为什么设备老是掉线，怎么修。**
> 现象：AGH 侧 `turpi-01` 反复从 available 变成 `not available`，
> 但进程一直活着、ROS 栈也正常。

---

## 一、根因：WebSocket 心跳超时

### 决定性证据（设备程序日志）

```
keepalive ping failed
asyncio.exceptions.TimeoutError: timed out while closing connection

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  File ".../websockets/asyncio/connection.py", line 845, in keepalive
    async with self.send_context():
websockets.exceptions.ConnectionClosedError:
  sent 1011 (internal error) keepalive ping timeout; no close frame received

turpi-01: state fields without a value yet: battery     ← 之后仍在空转
turpi-01: state fields without a value yet: battery
```

**关键点**：异常之后程序**没有退出**，还在刷日志 ——
说明 `dev.run()` 的异常被某处吞掉，程序继续运行但**不再重连**。

### 完整因果链

```
WiFi 链路短暂抖动 / 延迟
   ↓
WebSocket keepalive ping 超时
（websockets 库默认 ping_interval=20s, ping_timeout=20s）
   ↓
抛出 ConnectionClosedError (1011)
   ↓
设备程序没有重连逻辑 → 连接永久丢失
   ↓
进程还在（空转、刷 battery 警告），但连接已死
   ↓
AGH 侧判定 not available
```

| **WiFi 丢包** | `ip -s link show wlan0` | ⚠ `TX dropped: 5`（轻微） |

**唯一的可疑项是 WiFi**，而心跳超时正是**网络抖动的典型症状**。

## 三、三种掉线类型的对照

**"设备掉线"有三种成因，处理方式不同**（详见 `docs/成功关键因素全记录.md`）：

| 类型 | 进程 | 日志 | 僵尸 | 真因 |
|---|---|---|---|---|
| 1. 栈雪崩 | 在 | 停 | **大量** | `usb_cam` 崩 → `bringup` 拖死 |
| 2. 数据源枯竭 | 在 | 停 | 少 | 单节点死 |
| **3. 连接断开** | **在** | **停** | 少 | **WebSocket 心跳超时（本文）** |

> **三种的共同特征**：**进程都在**。
> 所以「进程还在」**完全不能说明它在工作** ——
> 判断健康要看**数据是否在推进**。

## 四、方案 A：给设备程序加重连（已实施）

### 4.1 问题代码

设备程序 `turpi_device.py` 的入口（只有一次尝试）：

```python
if __name__ == "__main__":
    try:
        asyncio.run(main())        # ← 抛异常后不重试
    except KeyboardInterrupt:
        pass
    finally:
        try:
            bridge.stop_chassis()
            bridge.centre_gimbal()
        except Exception:
            pass
```

**`main()` 内部只有 `try/finally`，外层也没有重试循环。**

### 4.2 补丁内容

替换 `__main__` 块，加入**退避重连循环**：

```python
# ==== MHS-RECONNECT: 断线自动重连 ====
def _is_connection_error(exc):
    """判断是否为可重试的连接类异常。"""
    name = type(exc).__module__ + "." + type(exc).__name__
    text = f"{name} {exc}".lower()
    for key in ("connectionclosed", "keepalive", "timeout",
                "connectionreset", "connectionerror", "brokenpipe",
                "eof", "1011"):
        if key in text:
            return True
    return False


def _run_with_reconnect():
    """反复运行 main()，连接断了就退避重连。"""
    attempt = 0
    while True:
        try:
            asyncio.run(main())
            print("[reconnect] main() returned; reconnecting", flush=True)
            attempt = 0
        except KeyboardInterrupt:
            raise
        except Exception as exc:
            print(f"[reconnect] connection lost: {type(exc).__name__}: {exc}",
                  flush=True)

        attempt += 1
        delay = min(2 ** min(attempt, 5), 30)      # 2,4,8,16,30 封顶
        print(f"[reconnect] retrying in {delay}s (attempt {attempt})", flush=True)

        # 【安全】重连前确保底盘停止
        try:
            bridge.stop_chassis()
            bridge.centre_gimbal()
        except Exception:
            pass

        time.sleep(delay)


if __name__ == "__main__":
    try:
        _run_with_reconnect()
    except KeyboardInterrupt:
        pass
    finally:
        try:
            bridge.stop_chassis()
            bridge.centre_gimbal()
        except Exception:
            pass
```

### 4.3 三个安全设计

| 设计 | 作用 |
|---|---|
| **重连前 `stop_chassis()`** | 防止重连瞬间底盘失控 → **吸取 keeper v2 事故教训** |
| **退避重试**（2→4→8→16→30 秒封顶） | 避免疯狂重连打爆网络 |
| **识别连接类错误** | 只对连接问题静默重试，其他异常也打印原因 |

### 4.4 补丁脚本

`tools/add_reconnect.py` —— 特点：

- **精确文本匹配**：匹配失败**整体退出**，绝不半改
- **自动备份**：`.bak.<时间戳>`
- **幂等**：检测到 `MHS-RECONNECT` 标记则跳过
- **语法自检**：`py_compile` 失败**自动回滚**
- **只改 `__main__` 块**，不碰任何业务逻辑

## 五、踩到的坑：overlayfs 只读层

**补丁在容器内应用失败**：

```
PermissionError: [Errno 13] Permission denied: '/tmp/turpi_device.py'
```

**即使用 `docker exec -u root` 也一样失败。**

### 诊断结果

```
文件属主: ubuntu:ubuntu, 日期 Oct 10 13:02   ← 镜像构建时的原始文件
lsattr:   --------------e-------             ← 正常（e=extent）

root 可写 /tmp        ✓
可复制                ✓
直接写原文件          ✗ Permission denied    ← 关键
新文件可创建          ✓
```

**原因**：`/tmp/turpi_device.py` 在 **overlayfs 的只读下层（lowerdir）**，
容器内无法修改。

### 绕过方法（三步）

```bash
# 1. 宿主上的同名文件是可写的（md5 与容器内一致，已验证）
#    在宿主上打补丁
python3 /tmp/add_reconnect.py /tmp/turpi_device.py      # 宿主路径

# 2. 传到容器内的新路径
docker cp /tmp/turpi_device.py turbopi:/tmp/turpi_device_patched.py

# 3. 启动和 keeper 都指向新路径
python3 -u /tmp/turpi_device_patched.py ws://<hub>:4180
```

**验证一致性**（补丁前做的）：
```bash
docker cp turbopi:/tmp/turpi_device.py /tmp/_from_container.py
md5sum /tmp/turpi_device.py /tmp/_from_container.py
# 两者应相同 → 确认宿主文件就是容器那份
```

## 七、日志增长：不必担心

用户问「这条日志会不会冲爆磁盘」。**实测结论：不会。**

```
消息: turpi-01: state fields without a value yet: battery
来源: agnes_mhs/device.py:427（库打印的，不在设备程序里）

增长速率实测（30 秒采样）:
  T0:  6721 字节 / 136 行
  T30: 6773 字节 / 137 行
  → 约 1 行 / 30 秒
  → 约 120 行 / 小时
  → 约 2880 行 / 天 ≈ 144 KB/天

磁盘可用: 30 GB
→ 按此速率需数百年才写满，完全无风险
```

**没有 logrotate 针对 `turpi.log`**，但按上述速率也不需要。

### 但这条消息本身值得关注

`battery` 字段**始终拿不到值**，意味着：

> **低压保护仍然失效** —— `BATTERY_LOW_MV = 6800` 永不触发。
> 车会一直跑到硬关机（**已发生 3 次**）。
> **必须人工看电压**（`tools/bat.sh`）。

`battery_percent()` 在设备程序里（第 161 行），
读的是 ROS 话题 `/ros_robot_controller/battery` ——
而那话题存在**类型冲突**（设备订阅 `Float64`，厂商发布 `UInt16`），
这是 `battery` 拿不到值的直接原因。

## 八、遗留问题

1. **补丁不持久**：跑在 `/tmp/turpi_device_patched.py`，**容器重启后丢失**。
   需要在 keeper 或启动脚本里自动重新部署。
2. **`battery` 始终无值** → 低压保护失效，需人工盯电压。
3. **keeper 检测不到类型 3 掉线**：它只查「进程是否存在」。
   现在设备程序自己能重连了，**这个问题已被方案 A 缓解**。
