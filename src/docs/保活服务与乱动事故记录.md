# 保活服务与「车自行乱动」事故记录

> 2026-10-11。**这是一次我（AI）自己造成的事故，必须完整记录。**
> 起因：我加的保活脚本设计有缺陷，导致车在无人指令时反复动作。

---

## 一、事故现象

用户报告：**"我现在没给小车发指令，它刚才还在乱动。"**

AGH 侧设备状态：`connected, not available`，位置持续变化。

---

## 二、根因：keeper v2 的两处设计错误

### 错误 1：用「日志大小不增长」判定卡死（误判）

v2 的逻辑：

```
每 30 秒检查 /tmp/turpi.log 的大小
连续 6 次（3 分钟）不增长  →  判定「设备程序卡死」→ kill -9 并重启
```

**为什么错**：设备程序在**稳定工作状态时本来就很少写日志**
（只在状态变化时输出）。日志不增长**不等于**卡死。

**实际日志证据**：

```
[10-11 08:36:15] 设备程序不在 → 启动
[10-11 08:40:00] 设备卡死(日志 3 分钟未增长) → 重启     ← 误判！
```

### 错误 2：重启设备程序前未先停机

`turpi_device.py` 启动时会**初始化底盘**，可能触发运动指令。
v2 直接 `kill -9` 然后重启，**没有先发零速指令**：

```
kill -9  →  电机可能保持最后的指令
         →  重启时初始化底盘  →  车动
         →  3 分钟后日志又没增长  →  再重启  →  循环
```

### 事故链条

```
日志 3 分钟没增长
   → 误判「卡死」
   → kill -9 + 重启设备程序
   → 设备程序初始化底盘 → 车动
   → 3 分钟后日志又没增长
   → 再次误判 → 再重启 → 车再动  ← 循环
```

## 三、止血措施（已执行）

```bash
# 1. 停 keeper
kill -9 $(cat /tmp/keeper.lock)

# 2. 停设备程序
docker exec -u root turbopi pkill -9 -f turpi_device.py

# 3. 硬发零速
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.0}, angular: {z: 0.0}}'
```

**止血后确认**：
- keeper 进程数 = 0
- 设备程序进程数 = 0
- `/cmd_vel` 用 `--verbose` 查 **Publisher count: 0**
- 12 秒监听内**无任何消息**

> ⚠ **一个重要澄清**：当时 `ros2 topic info /cmd_vel`（不带 `-v`）显示
> `Publisher count: 1`，但那是 `kill -9` 后**残留的 DDS 注册记录**，
> 不是真有人在发。用 `-v` 或实测监听才能看到真相。

## 四、keeper v3：修正后的设计

### 安全原则

| 原则 | 说明 |
|---|---|
| **不猜测** | 删掉「日志卡死」判定，**仅在进程完全消失时**才拉起 |
| **先停机再动** | 任何设备程序启停前后，**先发零速 + halt** |
| **冷却期** | 同类动作最小间隔 **600 秒** |
| **安全默认** | 「自动重启卡死」**默认关闭**，需 `AUTO_RESTART_DEV=1` 显式开启 |

### 保留的可靠判据（这些不会误判）

| 检查项 | 判据 | 可靠性 |
|---|---|---|
| 僵尸进程数 | `> 8` | ✅ 可靠 |
| `mecanum_chassis_node` | 进程缺失 | ✅ 可靠 |
| `usb_cam` | 进程缺失 | ✅ 可靠 |
| `web_video_server` | 进程缺失 | ✅ 可靠 |
| 设备程序 | 进程缺失 | ✅ 可靠 |
| ~~日志大小不增长~~ | ~~判卡死~~ | ❌ **已删除** |

### v2 → v3 对照

| 项 | v2（事故版本） | v3（现行） |
|---|---|---|
| 卡死判定 | 日志 3 分钟不增长 | **已删除** |
| 重启条件 | 疑似卡死 + 进程消失 | **仅进程消失** |
| 重启前停机 | ❌ 无 | ✅ **先发零速** |
| 动作冷却 | 无 | **600 秒** |
| 自动重启卡死 | 默认开 | **默认关** |

## 七、这次事故的教训

1. **自动重启类逻辑必须默认保守**
   我为了「自愈」把判据设得很激进，结果**制造了比原问题更严重的故障**。

2. **不可靠的判据比没有判据更危险**
   「日志大小不增长」看起来合理，实际会误判。
   **宁可漏报，不可误报** —— 尤其在涉及物理运动的场景。

3. **涉及运动的自动化，必须先确保安全状态**
   任何设备程序重启前**必须发零速**。这是机器人控制的基本要求，我漏了。

4. **看进程/注册表不如实测**
   `Publisher count: 1` 是 DDS 残留注册，
   **实测监听 12 秒无消息**才说明真没人发。

5. **加自动化前应先问：它出错时会怎样？**
   keeper 出错 = 车乱动。**这个代价远大于它带来的便利。**
   正确顺序应是：**先加安全闸，再加自动化。**

---

## 八、给后来者的提醒

> **如果有人要给 TurboPi 加自动重启/保活逻辑：**
>
> 1. **先发零速再动任何设备程序**（`safe_stop()`）
> 2. **不要用日志大小判存活** —— 用进程存在性
> 3. **动作加冷却期**（≥ 10 分钟）
> 4. **默认关闭一切会触发物理动作的自动化**
> 5. **任何异常动作，先 `systemctl stop turpi-keeper`**
