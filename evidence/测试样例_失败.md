### F1 · 双进程互踢（协议级失败）✅ 已定位并修复

| 项 | 内容 |
|---|---|
| **类别** | 失败 —— 协议冲突 |
| **现象** | `turpi-01` 每 **30–60 秒**掉线一次；活动日志出现 `1006` 与 `Nerve channel closed`；socket 端口不断变化（重连）；send-Q 堆积 **100–250 KB**；**日志停在 `audio: speaker unmute ok` 之后不再增长**；进程活着、socket 在、但数据不流 |
| **根因** | **两个** `turpi_device.py` 进程同时在跑，**共用同一 device id `turpi-01`**。`agnes_mhs/device.py` L443：`"replaced by another connection with the same id; not reconnecting"` —— 同 id 新连接会踢掉旧连接，且被踢者不再重连。两个进程反复抢占，一个占着 socket 却什么都不做。 |
| **排查难点** | 症状与"网络问题"极难区分，**误导了很长时间** |
| **佐证** | 实测 `ps` 输出：`PID 20820 PPID 0`（本次启动的）与 `PID 34826 PPID 2113`（更早的残留） |
| **修复** | `tools/clean_restart.sh`：容器内与宿主都清理 → 验证 socket 清空 → **只启一个** |
| **修复后对比** | 日志：从不输出 `speaker unmute` → **首次完整走通启动流程**；进程数：2 → **1（PPID 0）**；socket：反复变化 → 建立两个通道（命令 + nerve），符合设计 |
| **教训** | **启动前必须确认进程数为 0。** 每次重启前不检查，就会再次变成双进程互踢 |

**这条例子的价值**：展示了「设备侧行为违反协议假设 → 系统出现难以归因的间歇故障 →
通过证据定位根因 → 修复并建立预防判据」的完整闭环。

### F2 · 电池字段恒空 → 低压保护失效（上游依赖失败）⚠ 已定位，**未修复**

| 项 | 内容 |
|---|---|
| **类别** | 失败 —— 上游依赖缺失导致安全机制失效 |
| **现象** | 设备日志反复输出 `turpi-01: state fields without a value yet: battery` |
| **排查过程** | 发现设备**不通过串口 SDK 读电池**，而是订阅 ROS2 话题 `/ros_robot_controller/battery`。实测该话题：`Publisher count: 0`（**无任何发布者**），`Subscription count: 1`（只有我们的设备在订阅）。即 `ros_robot_controller` 节点在跑，但**没有发布电池话题**。 |
| **根因（排查过程中的假设）** | 厂商节点 `ros_robot_controller_node.py` 存在**名字遮蔽 bug**：L38 创建 publisher；L113 发布循环的门闩是 `if self.enable_reception:`；L126 `self.enable_reception = msg.data` **把方法名重新绑定成了 bool**。而 L27 只调了**板子**的 `self.board.enable_reception()`，发布循环看的是**节点自己**的 `self.enable_reception` —— 两者不是一回事。另存在类型冲突：L38 声明 `UInt16`，`ros2 topic list -t` 报为 `Float64`。 |
| **⚠ 根因更正（2026-10-11）** | 上述「名字遮蔽 bug」是**真实存在的代码缺陷**，但它是否就是电池话题无发布者的原因**尚未证实**（当时 DDS 发现也曾损坏）。而**低压保护失效的另一个更底层原因已查明并推翻旧结论**：串口接收缓冲区积压陈旧数据，读前未 `reset_input_buffer()`。详见 `../../docs/小车接入实测记录.md` 开头「★ 头号陷阱」与 `../../docs/成功关键因素全记录.md` 第二节 |
| **影响（**不只是少个字段**）** | ① `battery_percent()` 永不返回有效值；② **低电量安全闸失效** —— 设备 L760 的 `if mv is not None and mv < BATTERY_LOW_MV(6800): return "battery is ... charge before driving"` **永远不会触发**（`mv` 恒为 `None`），即**低电量时车不会拒绝运动指令**；③ `after` 钩子本应附带的 `battery_mv` 静默省略 |
| **实际后果** | **小车曾因此跑到电量耗尽硬关机，链路无任何预警地中断，排查被迫中止** |
| **缓解措施（已做）** | ① 电池值可**直读**（宿主侧 7306 mV）；② 建立电压分级判据（< 6900 mV 禁跑运动）；③ 写好修复脚本 `tools/fix_battery_topic.ps1`（**已语法验证，未应用**） |
| **状态** | ⚠ **未修复**。修法明确（四处精确文本替换），待小车可用时应用 |

**这条例子的价值**：展示了「**安全机制的失效往往不是显式报错，而是静默**」——
比"调用失败"更危险，因为它不会告诉你它坏了。

### F3 · `aim_camera` 云台恒失败（硬件限制）✅ 已知，**设计如此** —— 已有 AGH 调用记录

| 项 | 内容 |
|---|---|
| **类别** | 失败 —— 硬件能力缺失 |
| **现象** | `aim_camera` 调用**总是报错** |
| **根因** | 云台舵机**接受位置写入**（读回正确）但**带不动负载**（无扭矩）。且厂商 ROS2 代码存在**舵机 ID 冲突**（`servo_controller.yaml` 的 id 1/2 与云台冲突）。 |
| **系统设计选择** | **故意保留该工具**，让它如实报错，而不是从工具表里移除来掩盖硬件限制 |
| **降级方案** | 用 `change_view`（底盘转向）代替云台，实测 25–40° 效果好 |
| **状态** | ✅ 已知限制，已在文档中如实记录 |
| **✅ 新增：实测报错原文** | `turpi-01: aim_camera error (x_gimbal_unavailable): the pan-tilt gimbal does not move the camera on this robot (servo accepts the position but has no torque under load); use change_view to turn the chassis instead.` |
| **✅ 新增：证据** | 上个任务执行中真实调用了 `call_device(turpi-01, tool="aim_camera", args={"tilt":1700})` 并失败，完整记录在 `agh-diagnostics-8f055bc6-20261011-033532-*.zip` → `events.jsonl` |

**这条例子的价值**：这是一个**刻意的诚实设计** —— 让评委能看到系统对自身能力边界的
如实申报，而不是只展示能用的部分。

## 二、排查中已推翻的假设（避免重复劳动）

这部分本身就是**严谨排查**的证据 —— 说明结论不是猜的：

| 假设 | 推翻依据 |
|---|---|
| HTTP 取图饱和拖慢设备 | 快照接口实测 **0.07 s**，5 并发仅 **0.12 s** |
| 线程池饥饿（默认执行器耗尽） | 压测 200 并发取图，**线程数 15 与 socket 完全不变** |
| Windows 防火墙拦截入站 | 关闭 + 加规则后仍失败；**真因是双进程互踢** |
| 本机 IP 变了 | 实测仍是 `192.168.3.149`，ARP 确认属本机 WLAN |
| `front` 丢帧是主因 | 它是**症状**，随双进程互踢一起出现 |
| 车 → 本机 22/4177 失败 = 被防火墙拦 | **本机 22 未监听、4177 仅绑 `127.0.0.1`**，本就不对外 |
| `bash /dev/tcp` 探测可靠 | 同一时刻对比：`bash /dev/tcp` → FAIL，`python socket` → CONNECTED，`curl` → 200 |
