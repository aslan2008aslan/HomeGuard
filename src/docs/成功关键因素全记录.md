## 设备掉线的三种类型（务必区分）

> 2026-10-11 补充。**"掉线"是症状，不是原因。**三种成因的处理方式完全不同，
> 混为一谈会浪费大量时间。

### 判别总表

| 类型 | 进程 | 日志 | TCP 连接 | 僵尸 | 真因 | 处理 |
|---|---|---|---|---|---|---|
| **1. 栈雪崩** | 在 | 停止增长 | 已建立 | **大量(>8)** | `usb_cam` 崩溃拖死 `bringup` | 重启容器 + 拉栈 |
| **2. 数据源枯竭** | 在 | 停止增长 | 已建立 | 少 | `usb_cam`/`web_video_server` 单独死 | 单独拉起该节点 |
| **3. 设备程序卡死** | 在 | **停止增长** | 已建立 | 少 | 设备程序主循环阻塞 | 重启设备程序 |

**三种的共同特征**：**进程都在、TCP 都已连接**。
**所以"设备程序还在跑"完全不能说明它在工作。**

### 关键判据：日志是否还在增长

```bash
# 取两次，间隔 30 秒，比较大小
docker exec turbopi sh -c 'wc -c < /tmp/turpi.log'
sleep 30
docker exec turbopi sh -c 'wc -c < /tmp/turpi.log'
# 大小不变 = 卡死或数据源断了（无论进程在不在）
```

> ⚠ **不要只看 `ps` 有没有进程。** 本次两次掉线，进程**都在**，
> 但一次是 ROS 栈全死（22 个僵尸），一次是设备程序阻塞。

### 类型 1 实例：ROS 栈雪崩（22 个僵尸）

```
740 [ros2]              <defunct>
748 [mecanum]           <defunct>
750 [usb_cam_node_ex]   <defunct>
...共 22 个
```

**成因**：`usb_cam` 崩溃 → `bringup.launch.py` 主进程退出 → 所有子节点成孤儿僵尸。

**修复**：`docker restart turbopi` → 清僵尸 → 手动 `ros2 launch bringup` → 单独拉 `usb_cam`。

**教训**：**`usb_cam` 是单点故障。**它一崩，整栈雪崩。

### 类型 3 实例：设备程序卡死

**特征**：
- 进程在跑（PID 660，已运行 36 分钟）
- **日志 3 分钟未增长**（mtime 停在 `00:29:39`，当前 `00:32:27`）
- ROS 节点全部正常，快照 HTTP 200
- AGH 侧却报 `not available`

**成因**：设备程序主循环阻塞。日志一直刷
`state fields without a value yet: battery`（`battery` 字段拿不到值），
**这个等待可能把源推送卡住**。

**修复**：`pkill -9 -f turpi_device.py` → 重启设备程序。

## 保活方案：`tools/keeper.sh`

**每 30 秒检查一次，三层自愈。**

### 覆盖的检查

| 检查项 | 阈值 | 动作 |
|---|---|---|
| 僵尸进程数 | > 8 | 重启容器 + 拉栈 |
| `mecanum_chassis_node` | 缺失 | 重启容器 + 拉栈 |
| `usb_cam` | 缺失 | 单独拉起 |
| `web_video_server` | 缺失 | 单独拉起 |
| 设备程序 | 缺失 | 启动 |
| **设备程序日志** | **连续 6 次(3分钟)不增长** | **判卡死 → 重启** |

### 部署

```bash
# 上传后执行
nohup setsid bash /tmp/keeper.sh ws://<hub-ip>:4180 > /tmp/keeper.log 2>&1 < /dev/null &
```

或用 `tools/deploy_keeper.sh` / `tools/restart_keeper.sh`。

### 查看状态

```bash
cat /tmp/keeper.log                              # 保活日志
ps -eo pid,args | grep 'bash /tmp/keeper.sh'     # 守护是否存活
```

### 踩过的坑（写脚本时注意）

1. **`grep -c` 可能返回多行**（`docker exec` 输出带提示行），
   直接比较会报 `[: 0\n0: integer expression expected`。
   **必须 `head -1 | tr -cd '0-9'` 归一化。**
2. **`pkill -f 'keeper.sh'` 会杀掉脚本自身**（命令行含该字符串）。
   **用 PID 文件或精确匹配 `bash /tmp/keeper.sh`。**
3. **`nohup ... &` 要通过 SSH 存活，必须加 `setsid`**，否则连接断开即被杀。

## 二、决定性转折：识别出「假故障」

**这是整件事最关键的一步。** 此前所有排查都困在同一个错误前提里。

### 错误前提

| 现象 | 错误结论 |
|---|---|
| SDK `get_battery()` 10 次全 `None` | "扩展板坏了" |
| `cat /dev/ttyAMA0` 0 字节 | "扩展板没通电" |
| 发 `0xAA55` 收到 0 字节 | "排线断了" |

**三条路径都指向"硬件故障"，看起来互相印证 —— 但它们共享同一个错误前提。**

### 真相

扩展板**一直在正常上报**，约 85 帧/秒：

```
aa55 00 03 04 9d1f 80 00
              └──┴─ 小端 0x1f9d = 8093 mV
```

**根因**：串口接收缓冲区积压陈旧数据，SDK 未清空缓冲就校验，全部失败。

### 决定性的判决实验

| 实验 | 结果 | 含义 |
|---|---|---|
| 清空缓冲**前**读电池 | `None` | — |
| 清空缓冲**后**读电池 | **8080 mV** | 立刻成功 |
| 发 32B 递增，看回读 | 回读**完全不同**（`aa55...`） | 不是回环 |
| **什么都不发**静置 3 秒 | **收到 256 字节** | **设备在主动上报** |

> **关键判据**：不发也在收 + 回读内容与发送无关 → **线路上有活跃设备，不是故障。**

### 教训

1. **"读不到数据" ≠ "设备坏了"** —— 先怀疑读取姿势
2. **多个"独立证据"可能共享同一错误前提** —— 会形成假印证
3. **必须设计判决性实验** —— 这次是"清空缓冲前后对比"
4. **不要急着下"硬件故障"结论** —— 会导致拆机、返修等大代价动作

## 三、成功的关键因素（可复用的方法论）

### 1. 一次跑完全套诊断，不做多轮

**背景**：车曾因低压保护失效（`mv` 恒 `None`）反复断电，排查三次都中断。

**做法**：写 `tools/post_power_on.sh`，一次跑完系统/串口/容器/电池全部检查。**避免"排查到一半断电"丢失结果。**

### 2. 每步都有可证伪的判据

| 步骤 | 判据 |
|---|---|
| 设备程序启动 | 进程数 **恰好 1**，日志**字节数增长** |
| 串口通 | 电池读到**具体数值** |
| 图像通 | 快照 **HTTP 200 + 字节数 > 0** |
| 车运动 | **目视画面位移**（不看 `drive` 返回值） |

### 3. 不信开环返回值

`drive` 返回 `drove 0.45 m forward` **完全不能证明车动了**：

```python
self.cmd_pub.publish(t)     # 不报错
self.odo.integrate()        # 纯软件累加
```

**唯一可信验证是画面变化。** 这次对比前后照片（物体变大、下移）确认了真实位移。

### 4. 用"能区分假设"的实验，而不是"支持假设"的实验

**错误做法**：反复发探测帧，每次没回应就更确信"坏了"。

**正确做法**：设计一个**能区分两种可能**的实验 ——
"发数据看回读" 只能得到"有/无"，而 "什么都不发看是否有数据" 能区分**主动上报 vs 静默**。

### 5. 僵尸进程要单独查

`front` 无图像的真因：

```
usb_cam_node_exe     <defunct>     ← 僵尸
web_video_serve      <defunct>     ← 僵尸
8080 无监听
```

**进程列表里有名字 ≠ 进程活着。** 必须看 `STAT` 列（`Z` = 僵尸）。

### 6. 命令要写进脚本文件

PowerShell 5.1 会吃掉 `$PYTHONPATH`、解析引号里的 `|`。
**所有复杂命令写进 `.sh`，用 `pscp` 传过去执行。**

### 7. 日志重定向放在引号内部

```bash
# 错：日志永远 0 字节
docker exec -d ... zsh -c 'cmd' >> /tmp/x.log 2>&1
# 对：
docker exec -d ... zsh -c 'exec cmd >> /tmp/x.log 2>&1'
```

## 五、仍未解决 / 有明确限制的

### 1. 云台不可用（硬件限制，无法绕过）

```
aim_camera error (x_gimbal_unavailable):
the pan-tilt gimbal does not move the camera on this robot
(servo accepts the position but has no torque under load)
```

**后果**：镜头固定在**水平朝前**，**无法俯视**。
→ 拍不到低于镜头且贴近的物体（如花盆上的仪表）。
**替代**：靠车身移动改变视角；或人工读取。

### 2. 低压保护失效

`mv` 恒 `None`，永不触发保护，车会跑到硬关机（**已发生 3 次**）。
**对策**：必须人工看电压 `tools/bat.sh`。

### 3. 无土壤湿度传感器

现有 5 个设备**均无测土壤湿度能力**：
`env-01` 测的是**空气湿度**（41.25%），不能代表土壤含水量。
**对策**：需接入电容式土壤湿度传感器。

### 4. `pose` 不可信

无编码器，纯航位推算，会漂移。设备自己也报 `position not trusted`。
