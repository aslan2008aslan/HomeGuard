### 0.3 【★ 待验证】假设：扩展板实际接在 USB 上，`/dev/rrc` 指错端口

> 2026-10-11 提出，**同日已被实验推翻**（USB 无数据，扩展板实际走 ttyAMA0）。
> 保留可见：这是一个**合理的假设**，只是不成立。

**线索**：USB 总线上有一个 CH340 串口转换器：

```
Bus 001 Device 003: ID 1a86:7523 QinHeng Electronics CH340 serial converter
  → /dev/ttyUSB0   (ID_MODEL=USB_Serial)
```

而 `/dev/rrc -> ttyAMA0`（GPIO 14/15 串口）。

**假设**：若扩展板实际是**通过 USB 转串口线**连树莓派的，
则 `/dev/rrc` **指错了端口** —— 恰好能解释「发数据出去、零回应」。

**验证方法**（已实测，**假设不成立**）：

```python

PYTHONPATH=/home/pi/demo python3 -c "
import time, ros_robot_controller_sdk as rrc
b = rrc.Board(device='/dev/ttyUSB0')   # 关键：改设备路径
b.enable_reception()
time.sleep(1)
print('battery:', b.get_battery())
"
```

**若读到数值** → 假设成立，修复方式是改 `/dev/rrc` 软链或 SDK 的设备路径。

**实物可快速确认（比软件试更快）**：
1. 扩展板与树莓派之间是**排线（GPIO 14/15）**还是 **USB 线**？
2. 扩展板指示灯是否亮（有无供电）？

## 2. 【最关键】先测电量，再决定能不能跑

上次就是**没看电量直接跑**，最后电池耗尽硬关机，链路毫无预兆地断。

### 1.1 直读电压（宿主，不是容器）

```bash
plink -ssh -batch -i $KEY pi@192.168.3.187 "cat > /tmp/bat.sh <<'EOF'
PYTHONPATH=/home/pi/demo python3 - <<'PY'
import time, ros_robot_controller_sdk as rrc
b = rrc.Board()
b.enable_reception()          # 必须先调，否则全部返回 None
time.sleep(1.0)
for i in range(6):
    print('battery =', b.get_battery(), 'mV')
    time.sleep(0.3)
PY
EOF
bash /tmp/bat.sh"
```

**实测参考值**：上次读到 **7306 mV**，稳定在 7303–7308 mV。

| 电压 | 含义 | 建议 |
|---|---|---|
| ≥ 7600 mV | 充满 | 可长时间跑演示 |
| 7200–7600 mV | 充足 | 可跑 |
| 7000–7200 mV | 偏低 | **只做短测试** |
| < 6900 mV | 危险 | **别跑运动**，先充电 |
| < 6800 mV | 设备本应拒绝驱动 | 但**该保护已失效**（见下） |

### 1.2 【重大坑】低电量保护是失效的

设备自己的安全闸在 `turpi_device.py` L760：

```python
if mv is not None and mv < BATTERY_LOW_MV(6800):
    return "battery is ... mV; charge before driving"
```

但 `mv` 恒为 `None`（上游话题无发布者），所以 **`mv is not None` 永远为假**
→ **这条保护永远不会触发**。即：**电量再低，车也不会拒绝运动指令，会直接跑到关机。**

**结论：演示前必须人工看电压，不能指望车自己保护自己。**

### 1.3 【已废弃】电池话题补丁 `fix_battery_topic.ps1`

> ❌ **该补丁已废弃，脚本已删除，不要再应用。**
>
> **原因**：它基于一个错误的前提 —— 以为电池读不到是因为厂商代码里的
> **名字遮蔽 bug**（`self.enable_reception` 被消息覆盖）。
>
> **真相**：电池读不到的真因是**串口缓冲区积压陈旧数据**，
> 读前 `reset_input_buffer()` 即可，实测读到 **8080 mV**。
> 与厂商代码的名字无关。
>
> 详见 `docs/成功关键因素全记录.md` 第二节。

> 附带教训：**一个补丁写得再严谨（自动备份、幂等、原子操作），
> 前提错了就没有价值。**先确认根因，再写补丁。

## 3. 启动设备程序：必须先清残留

### 2.1 【最坑】双进程互踢

上次排查花了很久，就是因为它。**两个 `turpi_device.py` 进程共用同一 device id 会互相踢**，
`agnes_mhs/device.py` L443：

```python
log.error("%s: replaced by another connection with the same id; not reconnecting", self.id)
```

症状（很难与“网络问题”区分）：

- 设备反复上线/离线，活动日志出现 `1006` 与 `Nerve channel closed`
- socket 端口不断变化，send-Q 堆积 100–250 KB
- **日志停在 `audio: speaker unmute ok` 之后不再增长**
- 进程活着、socket 在、但数据不流

**铁判**：启动前进程数必须为 **0**；启动后必须为 **1**。不是 1 就别往下跑。

### 2.2 用脚本启动（已修好三处缺陷）

```powershell
& "C:\Program Files\PuTTY\pscp.exe" -batch -i $KEY tools\clean_restart.sh pi@192.168.3.187:/tmp/clean_restart.sh
plink -ssh -batch -i $KEY pi@192.168.3.187 "sed -i 's/\r$//' /tmp/clean_restart.sh; bash /tmp/clean_restart.sh"
```

脚本会：清除**容器内与宿主**全部同脚本进程 → 验证 socket 清空 → 只启一个 → 验证日志增长。

### 2.3 启动相关的四个坑（已验证）

| 坑 | 症状 | 正解 |
|---|---|---|
| **必须 `source ~/ros2_ws/.zshrc`** | `ModuleNotFoundError: No module named 'rclpy'` | 不能省，它提供 rclpy |
| **重定向位置** | 日志永远 0 字节或内容陈旧 | `>> /tmp/turpi.log 2>&1` 要放在 `-c` 引号**内部** |
| **`bash /dev/tcp` 探测不可靠** | 空报 FAIL，拦住本该成功的启动 | 用 python socket 探测 |
| **PowerShell 吃 `$PYTHONPATH`** | `zsh:export:1: not valid in this context: /tmp` | 命令写进 `.sh` 文件执行 |

正误对比：

```bash
# 错：重定向在外层，重定向的是 docker 自己的 stdout（空的）
docker exec -d ... /bin/zsh -c "..." > /tmp/turpi.log 2>&1

# 对：重定向在内层，由容器内 shell 执行
docker exec -d -u ubuntu -w /home/ubuntu turbopi /bin/zsh -c \
  "source ~/ros2_ws/.zshrc >/dev/null 2>&1; export PYTHONPATH=/opt/agh_mhs/python/src:\$PYTHONPATH; cd /tmp && exec python3 -u /tmp/turpi_device.py ws://192.168.3.149:4180 >> /tmp/turpi.log 2>&1"
```

> ⚠ **`192.168.3.149` 是开发机自己的 IP**，换网络环境会变。启动前先核实：
> `Get-NetIPAddress -AddressFamily IPv4 | Where-Object {$_.IPAddress -like "192.168.*"}`

## 6. 运动测试（**先做 §0.1 的 DDS 检查**）

> ⚠ **前提**：`ros2 topic info /cmd_vel` 的 `Subscription count` 必须是 **1**。
> 是 0 的话，下面怎么做车都不会动。

### 5.1 按此顺序，一步一验

```python
# 1. 确认可用（跑完 §4 全部判据）
read_device(device="turpi-01", sources=["pose"])

# 2. 先确认急停通道活着
call_device(device="turpi-01", tool="halt")

# 3. 低速短距离（首次：垫高车轮，**用眼睛看轮子**）
call_device(device="turpi-01", tool="drive", args={"distance": 0.4, "speed": 0.1})

# 4. 取图
read_device(device="turpi-01", sources=["front"])
```

### 5.1.1 【重要】怎么判断车真的动了

**不要相信 `drive` 的返回值。** 它是开环的（见 §0.2）。

| 方法 | 可靠度 |
|---|---|
| `drive` 返回 `drove 0.50 m forward` | ❌ **无意义**（发到没人收的 topic 也返回成功） |
| `pose` 位置数字变化 | ❌ **无意义**（纯软件航位推算） |
| **目视轮子转动** | ✅ **唯一可信** |
| 两张照片对比 | ⚠ 可参考，但相机被挪动过会干扰判断 |

### 5.2 运动前必须知道的限制

| 限制 | 后果 |
|---|---|
| **`/cmd_vel` 无订阅者**（已修，见 §0.1） | 修好后仍因串口故障不动（§0.2） |
| **无编码器**，位置靠航位推算 | `pose` 自标 `not trusted`，会漂移 |
| **低压保护失效**（§2） | 电量低也会跑，跑到关机；人工看电压 |
| `aim_camera` 总是失败 | 可能与串口/DDS 有关，不只是「硬件无扭矩」（见 §0.2） |
| `front` 有丢帧 | 正常现象（见下），看 `age` 不看百分比 |

### 5.2.1 【已解谜】`front: 87% lost` 不是故障

实测确证：这是 **MHS 的「最新优先」队列设计**（STR-6/STR-1）：
车发得比 hub 消费快，旧帧被替换，seq 跳过，hub 计为 lost。

**持续读图后 lost 会降到 `ok`**（有人消费，队列不积压）。

> **判据：看 `age`（秒级即正常），不看 `lost` 百分比。**
> 演示前不妨先读一次图，「唤醒」队列。

### 5.3 安全红线

- **不要带坏掉的源发运动指令**：`front`/`pose` 无数据时，先查链路
- **急停随时可用**：`stop_device` 总是允许的
- **在 §0.2 的串口问题解决前，不要指望运动**

## 架构决策：保持 MHS + ROS2（方案 A）

> 2026-10-11 决定。记录**为什么不换架构**，避免后来者重复讨论。

### 背景

收到了外部建议（豆包对话），主张：
**"停掉 ROS2 Docker，直接让 MHS 驱动调厂商 SDK 控制底盘"**，理由是链路更短、省内存、坑更少。

**经核实，对本项目不适用。** 理由如下。

### 理由 1：MHS 设备驱动已经写好并跑通了

我们**不需要**从零写驱动。`device/turpi_device.py` 已实测可用：

| 能力 | 证据 |
|---|---|
| 接入 AgnesHub | `turpi-01` available |
| 拍照 | 640×480 JPEG 进模型上下文 |
| `listen` / `say` / `halt` | 实测调用成功 |
| 正确申报工具与源 | 7 工具 + 3 源，AGH 侧可见 |

外部建议的适用场景是"没有现成驱动、从零开始"，**我们的卡点不在这里**。

### 理由 2：停掉 ROS2 等于自断电机链路

厂家**把麦轮运动学写在 ROS2 节点里**：

```
/cmd_vel
  → mecanum_chassis_node         ← 厂商的 ROS2 节点，做四轮差速换算
  → /ros_robot_controller/set_motor_speeds  实测 [-15/+15]
  → ros_robot_controller          ← 厂商的 ROS2 节点，写串口
  → /dev/ttyAMA0
```

停掉 ROS2，就得**自己实现麦轮解算**，工作量大增，且丢掉厂商已验证的逻辑。

### 理由 3：串口不通时，换架构也一样动不了

**当前唯一卡点一度被认为是“扩展板串口无响应（硬件层）”，已查明是误判。**
三条“独立路径”共享同一个错误前提（未清空缓冲区）：

```
1. SDK 读电池（已开 enable_reception）→ 10 次全 None
2. raw cat /dev/ttyAMA0              → 0 字节
3. 主动发 0xAA55 探测帧               → 发出成功，收到 0 字节
```

而厂商**自带的 SDK 也同样读不到**。**说明问题不在 MHS、不在 ROS2、不在驱动写法。**

### 理由 4：外部建议中的 API 与真实不符

为免后来者被误导，记录核实结果：

| 那份建议写的 | 真实情况 |
|---|---|
| `from mhs_device import MHSDevice` | 真实库是 **`agnes_mhs`** |
| `@dev.on_write` / `@dev.on_read` | **不存在**；真实模型是 `@dev.tool` + `dev.source` |
| `from turborpi import TurboPi` | **不存在** |
| `turbo.set_speed(speed, speed)` | 真实是 `board.set_motor_duty([[id, 占空比]])` |

> 那份内容自己也标注了"AI 生成可能有误 注意核实"。

### 但它有一条提示是对的

> "串口路径可能是 `/dev/ttyAMA0` 或 USB 转串口 `/dev/ttyUSB0`"

**这与我们的头号待验证假设吻合，见 `docs/恢复后待办与验证清单.md` §0.3。**

### 结论

**保持 MHS + ROS2（方案 A），优先查串口。**
串口恢复后，`/cmd_vel` 链路已通（实测 `Subscription count: 1`），车即可运动。

**只有在串口恢复正常、但 ROS2 路线确证走不通时**，才考虑"绕开 ROS2 直连 SDK"作为备选，
且那时仍需自己处理麦轮解算。
